## Core rule

Add Employee is now a native vertical slice. The Employees page and permission-gated modal use the platform API. Creation validates the work-email domain, department, designation, role and reporting manager; writes an Employee entity with a generated code; provisions a pending identity; creates and enrolls an Onboarding Case; and stamps eight tasks. A repeat request with the same idempotency key returned the same Employee and task count. One local demo hire exists alongside the 26 imported Employees. The read-only reconciliation now checks imported rows for drift while accepting additional native Employees and checking all target employee codes, emails, identity links and memberships. The creation operation still spans multiple platform service transactions; concurrent creation and interruption recovery need stronger guarantees before production use.

The native Onboarding page projects the case, employee name, ordered template steps, task statuses, assignee names, due dates and prerequisites. It makes the current next actions visible without treating the eight tasks as eight workflow states. An assigned owner or an HR manager can complete a ready step from this page; the backend serializes dependency checks and completion per case. The final platform transition requires all eight tasks complete and an HRMS onboarding management grant. Assignees see only cases with their tasks. The generic onboarding pipeline shortcut redirects to this scoped view instead of granting assignees broad entity access. The template defines no formal approval gates yet; HRMS will need explicit approval transitions where policy requires them. Completion actor audit, invitation delivery and domain outputs from steps remain production gaps.

For each HRMS business object, the platform entity record and enrolled workflow state become authoritative. HRMS domain code supplies only rules that cannot be expressed safely as generic fields, guards, relations, and transition permissions. An HRMS `status` column must not independently decide an approval after cutover. A temporary legacy-to-platform ID mapping is allowed for migration, but bidirectional writes are not.

The target entity catalog is organization-scoped and versioned. Form schemas hold editable fields and per-state presentation. Published state-machine definitions hold states, transition triggers, required fields, roles and approval actions. Platform transition execution owns state, idempotency, audit, and tasks; domain effects run through a tested action adapter with the same business operation boundary.

Current Leave limits before production: the Leave form/list is the only native employee-facing HRMS route; Timesheet, Project, Onboarding, Performance, Asset and Helpdesk still need entity-backed operations and UI cutover. Leave overlap validation is not serialized across concurrent create transactions, and it does not yet check submitted Timesheet entries or holiday policy. Leave lists are paginated by the API but the current UI displays the first 100 records. Employee manager lookup scans tenant Employee records; an indexed, tenant-scoped relationship will be needed at production scale. Field-level access for sensitive employee data, attachment migration, and role-by-role security tests remain required.

## Native workflow and approval design

### Add Employee and automatic onboarding (legacy parity)

The legacy `POST /employees` is one business operation, not just an Employee insert. It requires `employee_directory:create`, validates active department/designation options, the configured work-email domain, role, and reporting manager, creates a login identity and employee code, then starts onboarding from the default template and writes an audit event before commit. HR Basic, HR Full, and Super Admin can create; ordinary employees cannot. The native feature must preserve that contract. The legacy `count(*) + 1` employee-code generator is not safe under concurrent creation or deletion, so use a tenant-scoped sequence/unique constraint instead.

Native implementation sequence:

1. Extend `HRMS.Employee` with the legacy non-sensitive create fields (employment type, join date, work location, notice period, phone) in a versioned entity/form revision. Keep `platform_user_id`, employee code, organization, and manager linkage server-owned. Import existing values before enabling the new form. Department/designation options must come from tenant-scoped reference entities or picklists, not the frontend bundle.
2. Install scoped `HRMS HR Basic` and `HRMS HR Full` roles with an explicit `hrms:employee:create` grant, plus the appropriate view/edit grants. The native create route checks the *current database grant*, active organization membership, and tenant scope. Role choices are an allow-list; an HR Basic user cannot assign HR Full, admin, or other elevated roles. Never accept `platform_user_id`, employee code, or onboarding state from the client.
3. On submit, validate the normalized email and uniqueness, active reference values, manager in the same tenant and not offboarded, and valid role. Provision a pending platform user and suspended membership, create the `HRMS.Employee` entity, link them, and start one `HRMS.OnboardingCase` enrollment. Use an operation idempotency key, durable progress record/outbox, and retry/reconciliation so partial commits across platform services cannot leave a usable orphan account or a hire absent from onboarding. Activation/invitation occurs only through the approved onboarding step.
4. Stamp the versioned default onboarding template into platform tasks. The legacy default has eight steps: Newtuple ID, payroll account, HRMS invitation, profile, documents, assets, orientation, and project allocation. Preserve step order, assignee rules, dependencies, due-date offsets, completion actor and notes, and links to produced records. Task and workflow transitions must enforce dependencies server-side. Existing cases retain their template version when HR edits future templates.
5. Add an Employee Directory page to the HRMS skin with search/status filters and an Add Employee modal matching the legacy fields. Show the menu and button only to permitted roles, but enforce all access at the API. On successful create, show the new employee and linked onboarding case. Sensitive profile, payroll and bank fields must remain outside directory projections until field-level policy is proven.

Acceptance checks: HR Basic/HR Full/Super Admin can create within their allowed role choices; employees and managers cannot; cross-tenant manager IDs and elevated role IDs fail; duplicate email and idempotent retries are deterministic; a successful create yields exactly one pending identity, Employee entity, onboarding enrollment, eight assigned/dependency-aware tasks, and audit provenance; an interrupted step resumes without duplicates; directory/list/detail and indirect search/export views do not expose restricted fields.

The platform already supports entity types, form schemas/fields, published workflow versions, enrollment, transition roles, required fields, audit, idempotency and tasks. Use those services directly. The existing `backend/hrms/workflows/platform.py` only validates in-memory edges on legacy ORM assignments; it does **not** persist platform entity states or execute platform transitions. Replace that hook as each native flow goes live.

Start with Leave Request as a small approval path: create `HRMS.LeaveRequest` with employee, manager, dates, type and reason fields; install its form schema and `pending → approved/rejected/cancelled` definition; enroll each new request; execute approve/reject through `WorkflowServiceManager.execute_transition_for_actor`. The actor comes from the platform session/membership. The registered HRMS transition policy now checks approve/reject against the Employee's organization-scoped reporting relationship and cancel against the Employee's linked platform user; it ignores the editable Leave `manager_id` field. This check runs before idempotent replay and applies even to platform system roles. Successful transition replays are also bound to the original actor and trigger. Manager lookup currently scans Employee records and should be replaced with a persisted, indexed Employee relation before production scale. The existing `leave_requests` row becomes read-only migration source once the platform route is active. This vertical slice proves the architecture before the more complex timesheet, project amendment, onboarding and performance actions.

Other important state graphs from the source include Timesheet `draft → submitted → approved/rejected` (with rejected resubmission), Project Change `draft → pending → approved/changes_requested/rejected`, Job Opening `draft → pending_approval → approved → published`, and Performance Review `not_started → self_draft → submitted_to_manager → manager_submitted → calibrated → published → acknowledged`. Each needs actor-specific transition permissions and required-field checks. The approval history must come from committed platform transitions, not a separately edited JSON status history.

## Migration sequence and controls

1. Install a versioned `HRMS` product pack into a dedicated organization: entity types, relations and picklists, form schemas, workflow drafts/published definitions, then role policies. Installer must be idempotent and reject incompatible tenant edits rather than overwrite them.
2. Link each legacy user/employee to one platform user/membership; require server-derived organization and actor IDs. Prove employee, manager, HR and Finance access before importing sensitive records.
3. Import reference data and Employee, then Customer/Project, then dependent records. Maintain `(organization_id, source_table, source_id) → platform_entity_id` mapping with unique constraints and checkpoints. Import existing current state with original workflow version/provenance without firing tasks or notifications.
4. Reconcile counts, unique keys, relations, state totals, numeric totals, attachments and sample histories. Run the importer twice and require the second run to make no changes. Test interrupted batches and rollback.
5. Switch one module at a time to platform routes and stop legacy writes for that module. Keep specialized domain validation and side effects as platform action/guard adapters. Remove the old HRMS auth, duplicate state and status-write endpoints only after parity, security and browser journeys pass.

Do not put salary/bank data or approval authority into client-controlled generic JSON until the platform's field-level restrictions and membership checks are verified for list, detail, search, export and agent access. Organization ID on each row is necessary but does not by itself make a relationship between rows tenant-safe.
